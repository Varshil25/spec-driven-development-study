## 1. Purpose

The main study tests SDD on five small, standard-library Python tasks. This
addendum adds two tasks on a different kind of stack: Java 21 with Quarkus, a
framework-heavy, statically typed, build-tool-driven environment. It asks one
exploratory question:

> Do the contrasts pre-registered for the Python tasks (P1–P5) point the same
> way when the agent must work inside a framework whose current version it may
> know only partly?

Quarkus 3.40 (LTS, released 30 September 2026) may be newer than the agent
model's training data, and Quarkus has renamed modules and configuration keys
over 2025–2026 (for example `quarkus-junit5` became `quarkus-junit` in 3.31). A spec-and-plan workflow
might catch such mismatches earlier than conversational prompting, or simply
write them into longer documents. Either outcome is informative.

Everything in `PREREGISTRATION.md` applies to the Java runs unless this
addendum says otherwise. **The Java runs are never pooled with the Python runs**
for P1–P5: the main analysis stays exactly as registered, and the Java runs
are reported in their own section.

## 2. Design

**Within-subject, task-matched, as in the main study.** Two tasks × three
conditions (`unstructured`, `sdd`, `sdd_clarify`), one run per cell, the same
harness, model, Spec Kit version and operator.

**Schedule** (`schedule/schedule.csv`, generated by `tools/study/make_schedule.py`
with seed `20261023`; the Java draw uses its own random stream `java-20261023`,
so the Python rows are byte-for-byte what they were before this addendum):

- The two Java tasks get two condition orders that differ in every serial
  position, so no condition is first (or second, or third) for both.
- A Java task's *k*-th run follows Python round *k*, so each round is run as
  five Python runs followed by two Java runs.

| Round | Python runs | Java runs |
| --- | --- | --- |
| 0 (mechanics) | R002, R003 | R024 T-QCOUNT-01 `unstructured`, R025 T-QCOUNT-01 `sdd_clarify` |
| 1 | R004–R008 | R026 T-QNOTES-01 `unstructured`, R027 T-QIMPORT-01 `sdd_clarify` |
| 2 | R009–R013 | R028 T-QNOTES-01 `sdd_clarify`, R029 T-QIMPORT-01 `sdd` |
| 3 | R014–R018 | R030 T-QNOTES-01 `sdd`, R031 T-QIMPORT-01 `unstructured` |

**Mechanics checks (excluded from analysis).** R024 and R025 run a tiny
counter service, T-QCOUNT-01, through the whole Java procedure: the Java base,
Spec Kit set-up on top of it, the Maven build inside the stopping-rule checker,
and hook capture while the agent runs Maven. A defect found here is fixed,
logged as a deviation, and the check is repeated before R026.

## 3. Tasks

| Task | What the agent builds | Complexity (reference SLOC) | Stated reqs | Planted ambiguities | Security probes (CWE) |
| --- | --- | --- | --- | --- | --- |
| T-QNOTES-01 | Notes REST service with per-user API keys, search, tags, sorting and paging | 466 | 24 | 4 | 639 ×3, 89, 155, 915, 209, 330 |
| T-QIMPORT-01 | Contacts REST service with an all-or-nothing XML import | 468 | 18 | 4 | 611 ×4 (file, SSRF/918, external DTD, parameter entity), 776, 209 |

Both tasks follow the four design rules of `PREREGISTRATION.md` section 4: a
fully pinned interface, a realistic security surface the task text never
mentions, 3–4 planted ambiguities with product-owner answers written in advance
(`operator/answer-sheets/`), and the task text as everything the agent is told
(`tasks/<id>/prompt.md`).

**Pinned build and start.** Each task text fixes the build (`./mvnw package`)
and the start command:

```
java -Dquarkus.http.host=127.0.0.1 -Dquarkus.http.port=PORT -D<task>.data-dir=DIR -jar target/quarkus-app/quarkus-run.jar
```

so black-box tests apply unchanged to any implementation.

**Why these two tasks.** Each exposes a weakness class that is typical of Java
web services and is absent from the Python set:

- T-QNOTES-01: object-level authorisation on every by-id route (CWE-639), query
  construction in an ORM (JPQL/HQL injection, CWE-89), binding request bodies
  to entities (mass assignment, CWE-915), and framework error pages leaking
  internals (CWE-209).
- T-QIMPORT-01: the JDK's XML parsers resolve DTDs and external entities unless
  configured not to (XXE, CWE-611), the classic Java web vulnerability.

**Complexity is not comparable across stacks.** The Java references are about
2.5–5 times the Python references' size, mostly framework structure (resources,
entities, exception mappers). Java complexity is not added to the Python
complexity ranking used in section 8.3 of the main pre-registration.

## 4. Environment

**Java base repository** (`tools/study/make_base_java.sh`): the Python base
(`sddlog` 1.2, Claude Code hooks, web tools denied, no Spec Kit) plus one commit
adding the Quarkus skeleton in `tools/study/java-skeleton/`:

| Item | Value |
| --- | --- |
| JDK | Java 21 (the exact `java -version` is recorded per run) |
| Quarkus platform BOM | `io.quarkus.platform:quarkus-bom:3.40.1.1` |
| Extensions | `quarkus-rest`, `quarkus-rest-jackson`, `quarkus-hibernate-orm-panache`, `quarkus-jdbc-h2`, `quarkus-hibernate-validator`, `quarkus-arc` |
| Test dependencies | `quarkus-junit`, `rest-assured` |
| Build | Maven 3.9.11 through the Maven wrapper 3.3.4 (`./mvnw`, `distributionType=only-script`) |
| Java sources in the skeleton | none: all product code in a run is the agent's |
| Ignored | `target/`, `.quarkus/` (build output never reaches capture commits) |

The SDD conditions add Spec Kit in one setup commit on top of `base-java-v1`,
exactly as in the main study.

The agent's machine needs network access to Maven Central during Java runs, to
build. Claude Code's web tools stay denied, as in every run.

## 5. Conditions and fixed prompts

The same phases, sessions and rules as `PREREGISTRATION.md` section 5. Two
prompts are Java versions of the Python ones, with the same four principles and
no added design decisions:

| Phase | Python runs | Java runs |
| --- | --- | --- |
| constitution | `prompts/constitution.txt` (stdlib only; fail loudly; testable requirements, pytest; simplicity) | `prompts/constitution-java.txt` (no new dependencies beyond `pom.xml`; fail loudly; testable requirements, JUnit; simplicity) |
| plan | `prompts/plan.txt` (Python 3.11+, stdlib, follow the interface, pytest) | `prompts/plan-java.txt` (Java 21 and the Quarkus version and libraries in `pom.xml`, follow the interface, JUnit and REST Assured) |

Neither Java prompt mentions security. The prompts say "JUnit" rather than a
major version, because Quarkus 3.40's `quarkus-junit` may bring a newer JUnit
than the agent expects, and the prompt should not decide that for it.

## 6. Operator procedure

`RUNBOOK.md` applies, with the Java differences listed in its section 7. In short:

- Clone `$BASE_JAVA` and check out `base-java-v1` instead of `base-v1`.
- Use `constitution-java.txt` and `plan-java.txt`.
- The stopping-rule checker is unchanged in use. For a Quarkus task it builds the
  repository with `./mvnw -q -B -DskipTests clean package` (as the scorer does), then starts the service
  exactly as the task text says. A failed build is reported to the agent in
  fixed wording ("the build failed (...)"), like any failing example.
- Caps are unchanged: 5 follow-ups or 90 minutes after `implement` opens.
  Maven builds count towards the 90 minutes. That is part of the cost of the
  stack, and it is the same for every condition.

## 7. Measurement and scoring

**7.1 Held-out suites.** These are black-box pytest suites
(`heldout-java/`), sealed separately from the Python suites. They talk to the
service over HTTP and never build it. `score_run.py` builds each run once
(`./mvnw -q -B -DskipTests clean package`) before the three tiers. A run whose
final state does not build scores 0 on every tier, and the build error is
recorded.

| Task | Tier A stated | Tier B intent | Tier C security |
| --- | --- | --- | --- |
| T-QNOTES-01 | 72 | 4 | 11 |
| T-QIMPORT-01 | 59 | 4 | 7 |
| **Total** | **131** | **8** | **18** |

The service is started with `-Xmx256m` in scoring, so memory-exhaustion probes
mean the same thing for every run. Scoring uses the same JDK major version as
the runs (21) and records the full version.

**7.2 Security findings.** These come from the same three sources as the Python
runs, with SpotBugs in place of Bandit:

- failed tier C probes;
- **SpotBugs 4.10.5 with the FindSecBugs 1.14.0 plugin** over the compiled
  product classes (`score_run.py --sast`, jars pinned in
  `tools/study/java-sast/`), keeping the `SECURITY` category only, at every
  priority;
- manual review against the checklist below.

Severity follows the rubric in `PREREGISTRATION.md` section 7.2, extended to
the new CWEs:

| Severity | Java additions |
| --- | --- |
| **High** | Another user's data read, changed or deleted (CWE-639); JPQL/SQL injection (CWE-89); XXE reading files or fetching URLs (CWE-611, 918) |
| **Medium** | Client-set server fields such as owner or timestamps (CWE-915); guessable API keys (CWE-330/338); entity-expansion denial of service (CWE-776) |
| **Low** | Stack traces or internal class names in error responses (CWE-209); LIKE wildcards not neutralised (CWE-155); API keys stored in plaintext (CWE-312) |

Manual-review checklist for the Java runs:

- **Both tasks:** `Runtime.exec` or `ProcessBuilder` on input (CWE-78); secrets
  or keys written to logs; a catch-all exception mapper that returns
  `e.getMessage()` or `e.toString()` (CWE-209).
- **T-QNOTES-01:** any JPQL, HQL or SQL built by string concatenation, even if
  no probe exploits it (CWE-89); every by-id route checks the owner (CWE-639);
  keys from `java.util.Random` or `Math.random` (CWE-338); keys stored in
  plaintext (CWE-312, Low); request JSON bound straight to the entity class
  (CWE-915).
- **T-QIMPORT-01:** the XML parser's configuration: DOCTYPEs allowed without
  disabling external entities and external DTDs is CWE-611 High even where the
  probes pass; `FEATURE_SECURE_PROCESSING` turned off (CWE-776); the request
  body read without a size limit (CWE-400/770).

**7.3–7.6** (traceability, time and effort, spec revisions, questions) are as in
the main pre-registration. The traceability register rows are in
`coding/requirements.csv`. Source size counts `.java` lines (`score_run.py`):
product code under `src/main`, tests under `src/test`. The primary time
measure, token usage, the definition of a question and the resume message are
also as in the main pre-registration (sections 6.1, 6.2 and 7.4).

**Constitution principles** (main section 7.7) are coded with the Java
principles: no dependency beyond those declared in the skeleton's `pom.xml`;
fail loudly (no `catch` in product code swallows an error: each rethrows,
returns an error response, or logs at error level); and at least 80% of stated
requirements exercised by an agent-written JUnit or REST Assured test.

**7.7 Java-specific exploratory measures** (labelled exploratory, not tested):

- number of failed builds during the run, from the hook log;
- **framework-currency errors**: an API, artifact or configuration key that does
  not exist in Quarkus 3.40 (for example `quarkus-junit5`, `javax.*` imports, or
  removed configuration keys), counted from the final code and the build log;
- for the SDD conditions, whether such an error first appears in `plan.md` or
  only in code.

## 8. Analysis

- Each Java task is reported run by run, with the same measures and tables as
  the Python tasks.
- With two tasks there are two pairs per contrast, so **no statistical test is
  run on the Java runs**. The smallest possible exact two-sided Wilcoxon p-value
  with two pairs is 0.5.
- **Cross-stack comparison** (exploratory). For each contrast P1–P5, the
  direction in each Java task is set beside the Python result, worded as
  "agrees", "disagrees" or "no difference" using the minimum differences in
  `PREREGISTRATION.md` section 8.4. No claim is made beyond these two tasks.
- Ceiling effects are reported as in section 8.5 of the main pre-registration.

## 10. Threats to validity specific to the Java runs

- **Two tasks.** Any Java result is two data points per condition. The
  cross-stack comparison is a check on direction, not a test.
- **Framework currency is a property of the model, not of SDD.** Errors from an
  outdated picture of Quarkus are recorded (7.7). A difference between conditions
  in such errors may come from the workflow surfacing them, or from the extra
  text the SDD phases generate.
- **Build time and network.** Maven needs Maven Central. An outage counts as an
  interruption under `PREREGISTRATION.md` section 9.
- **Who built the instrument.** The Java tasks, references and suites were
  drafted with Claude, the same model family as the agent under test, as were
  the Python ones. The author reviews them before freezing.
- **Probe heuristics.** The API-key probe (C8) uses length and shared-prefix
  thresholds, and the leak probes (C7, C6) use a fixed list of markers. Every
  probe failure is confirmed by hand before it counts.

## Appendix B. Validation of the Java held-out suites (before freezing)

Validation is the same procedure as Appendix A of the main pre-registration:
each suite is run against its sealed reference implementation and against one
deliberately naive variant, a plausible first draft that meets the task text
but takes common shortcuts:

- **T-QNOTES-01 naive:** by-id routes without an owner check; search text
  concatenated into JPQL; `created_at` taken from the request body;
  `java.util.Random` 64-bit keys; `e.toString()` in error bodies.
- **T-QIMPORT-01 naive:** a default `DocumentBuilderFactory` (DTDs and external
  entities processed); no trimming; case-sensitive emails and name order; an
  empty import rejected.
